# Determining whether an Oura Ring 4 can run without an account

This document records the experiment used to determine whether the Oura Ring 4
can be claimed and read without an Oura account, and its outcome. The method is a
falsifiable test with a single decisive measurement.

## Hypothesis

The `auth_key` is a 16-byte shared secret between the ring and the phone, and it
is generated by the phone. If the phone generates the key, the phone must transfer
it to the ring at enrollment. The handshake uses a single static key with no
session keys and no per-message authentication. If the ring accepts a key the
phone provides during a factory-fresh window, then an independent application can
perform the same write with its own key and claim the ring without an account.

The question reduces to one measurable fact: does the `auth_key` travel over
Bluetooth during enrollment?

- Phone to ring: the write can be replicated. Account-free provisioning is
  possible.
- Ring to phone: the ring reveals the key; replicable if the read is not gated.
- Never on the wire: the key is cloud-derived or factory-burned, and this path is
  blocked.

Existing public captures are all post-enrollment, so none answer this. The test
requires capturing a factory-reset ring's first onboarding.

## Method

Required: the ring, the official Oura app, an iPhone, and a Mac. Resetting the
ring is reversible by re-onboarding.

1. Set up BLE capture. Install PacketLogger (from Apple's Additional Tools for
   Xcode) and the Bluetooth logging profile on the iPhone, then reboot. On Linux,
   `btmon -w enroll.btsnoop` writes a btsnoop log that also records packet
   direction.
2. Factory-reset the ring.
3. Start the capture.
4. Onboard the ring fully in the official app, through the first sync.
5. Stop and save the capture.
6. Analyze the capture. Locate the handshake nonce and proof, then test each
   16-byte value the phone wrote: if one value reproduces the proof under
   `AES-128-ECB(key, nonce ‖ 0x01)[:16]`, that value is the `auth_key`. Its
   presence as a phone-to-ring write answers the question.

A faster directional check is to factory-reset the ring, put the phone in airplane
mode with Bluetooth on, and attempt onboarding. If setup completes offline, the
key is established locally. If it blocks only at account login, the key can still
be set locally over BLE; if it blocks at the pairing or key step waiting on a
server, that indicates cloud gating. This check is suggestive but not decisive.

## Outcome

The capture shows the `auth_key` written from phone to ring over BLE during
enrollment, in the `24 10 <key>` key-set frame. A self-chosen key written to a
factory-reset ring is accepted and returns `status 0x00`. Account-free
provisioning is confirmed. The handshake math is implemented in the project's
Rust core (`oura_core::crypto`). The full frame sequence is described in
[ENROLLMENT_FINDING.md](ENROLLMENT_FINDING.md).
