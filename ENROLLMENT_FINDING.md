# Account-free key provisioning on the Oura Ring 4

This document describes how the `auth_key` is established on a factory-reset Oura
Ring 4, and how a device can be provisioned with a self-chosen key over Bluetooth
LE without an Oura account. The finding was derived from a Bluetooth capture of
the official onboarding flow on the author's own ring and validated against the
handshake math. It contains no captured data, no keys, and no Oura code.

## Background

Earlier public reverse-engineering of the ring captured only post-enrollment
traffic. As a result, outer-frame opcode `0x24` was documented as a firmware
authorization gate. A capture of a factory-reset ring's first onboarding shows
that `0x24` is also the key-provisioning command: during enrollment the phone
writes the 16-byte `auth_key` to the ring, then proves possession of it with the
standard handshake.

## The enrollment sequence

During first onboarding of a factory-reset ring, the central writes the key and
runs the handshake in the following order. All frames are written to the command
characteristic (handle `0x0015`) as ATT Write Requests.

| Step | Direction | Bytes | Meaning |
|---|---|---|---|
| 1 | central → ring | `08 03 00 00 00` | version / id probe |
| 2 | central → ring | `18 03 08 00 10` | subscribe category `0x08` |
| 3 | central → ring | `24 10 <key:16>` | key-set: opcode `0x24`, length `0x10`, then the 16 key bytes |
| 4 | central → ring | `2f 02 01 00` / `2f 02 01 01` | security config |
| 5 | central → ring | `2f 01 2b` | request nonce |
| 6 | ring → central | `2f 10 2c <nonce:15>` | 15-byte nonce |
| 7 | central → ring | `2f 11 2d <proof:16>` | proof = `AES-128-ECB(key, nonce ‖ 0x01)[:16]` |
| 8 | ring → central | `2f 02 2e 00` | status `0x00` (success) |

Because the key-set is an ATT Write Request, the direction is unambiguous:
central to peripheral. The handshake proof verifies the relationship between the
key written in step 3 and the proof returned in step 7, so the value written in
step 3 is confirmed to be the `auth_key`.

## Implications for account-free provisioning

The `24 10 <key>` frame carries the opcode, the length, and 16 raw key bytes. The
ring accepts the key the central provides during the factory-fresh enrollment
window. The key is generated by the central, so substituting an independently
generated 16-byte value is consistent with the protocol as designed.

This means a ring can be claimed without an Oura account: generate a random
16-byte key, write the key-set frame to a factory-reset ring, and run the standard
handshake. On `status 0x00` the ring is provisioned to that key, and the same key
authenticates on every subsequent connection.

## Status

Provisioning a factory-reset ring with a self-chosen key returns `status 0x00`
against real hardware. Account-free provisioning is confirmed end to end. The
handshake math used to verify the finding is implemented in the project's Rust
core (`oura_core::crypto`).
